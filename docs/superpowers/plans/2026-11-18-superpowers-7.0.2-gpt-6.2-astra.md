# Superpowers 7.0.2 for GPT-6.2 Astra implementation plan

**Goal** — Bring BetterGood’s 15 opt-in Superpowers workflows forward to upstream 7.0.2 and demonstrate that the packaged plugin works in Codex on `gpt-6.2-astra`.

**Approach** — Start from the pulled release. Compare the old fork against its own upstream parent, port each BetterGood behavior into its current location, and validate on the requested model. Preserve the company plugin identity so an existing installation has an upgrade path.

**Execution** — For a later authorized implementation, use `superpowers-gpt6:executing-plans` for native execution or `superpowers-gpt6:subagent-driven-development` if the human partner selects delegation. Use `writing-skills` for behavior changes. The items below are prospective checks.

**Stack** — Codex skills and plugin manifests, PowerShell 7+, Git, Bash, and the existing Node and Python test suites.

## Global constraints

- Keep `superpowers-gpt6`, display name **Superpowers GPT-6 — BetterGood**, selector `superpowers-gpt6@bettergood`, existing skill names, the `superpowers-gpt6:` Codex namespace, MIT attribution, and existing `.superpowers` plan workspaces. Proposed package version is **`7.0.2-gpt6.1`**, the first BetterGood revision of upstream 7.0.2. The model under test is **`gpt-6.2-astra`**.
- Keep model and effort session-selected. The inspected plugin has no OpenAI inference request builder. The model-specific executable change belongs in the evaluation runner, which previously invoked `gpt-6-astra`. The API migration guide’s request parameters, tool transport, and caching changes would apply to a direct API caller. [OpenAI migration quickstart](https://developers.openai.com/api/docs/guides/latest-model#migration-quickstart)
- Preserve host permissions, unrelated contributor requirements, compaction-friendly skill sizes, and the fork’s zero-dependency runtime. Local implementation, isolated tests, and packaging are the scope of a future implementation request. Commits, pushes, workspace sync, active-profile changes, employee installation, and upstream submission require separate direction. Keep existing user changes intact.

## Review focus

1. A plain coding request, an explicit workflow request, and a follow-up within an approved workflow route differently. Exercise all three through the installed package in Task 6.
2. Astra can pause on a routine choice or proceed past a real design decision. Test both directions in Tasks 1–2.
3. An installed helper can read a plan from the primary checkout while writing the ledger in a linked worktree. Exercise that topology in Task 3.
4. A detached checkout, a refused archive, or a clean commit range can conceal work still needing protection or review. Cover these in Task 4.
5. Source, both marketplace layouts, and the installed cache can each identify a different build. Verify their identities and hashes in Tasks 5–6.
